# 1.4.0 — plan

Status: decisions taken, nothing implemented. Written 2026-08-26 against
`main` at 1.3.0; open questions resolved the same day (see *Decisions* at the
foot).

Three things are wanted for 1.4.0:

1. **LiteLLM** as the way models are reached, alongside watsonx, plus OpenAI- and
   Anthropic-compatible endpoints wherever they are not already reachable.
2. **Per-user API keys entered in the UI**, stored as write-only secrets.
3. **A user management console** where an admin — an email named in `.env` — grants
   other addresses admin / full / judge / read-only.

They are ordered deliberately. (1) is self-contained and pays off immediately.
(2) and (3) both change what the server persists about people, and (2) is much
safer to build once (3) exists to say who may do it.

---

## What is actually there today

Worth stating precisely, because the current state is less uniform than
`CLAUDE.md` implies. Three call sites each dispatch on the model-name prefix, and
**each supports a different set**:

| Call site | Accepts |
|---|---|
| [`agentic_pipeline._create_llm_client`](../../../src/text2sql_eval_toolkit/inference/agentic_pipeline.py#L356) | `wxai:` `gemini:` `anthropic:` `vllm:` `openai:` `rits` |
| [`baseline_llm_pipeline`](../../../src/text2sql_eval_toolkit/inference/baseline_llm_pipeline.py#L78) | `wxai:` `gemini:` `vllm:` |
| [`llm_as_judge`](../../../src/text2sql_eval_toolkit/evaluation/llm_as_judge.py#L85) | `wxai:` only |

So `anthropic:claude-...` runs an agentic pipeline and raises `NotImplementedError`
on the baseline; no judge config can name anything but watsonx. The answer to
"is OpenAI/Claude already supported" is *partly, in one of three places*.

Behind those prefixes are six hand-written clients in `inference_tools.py` —
`WXAIClient`, `WXAIClientChatAPI`, `VLLMClientChatAPI`, `ClaudeClientChatAPI`,
`OpenAIClientChatAPI`, `GeminiClientChatAPI`. `ClaudeClientChatAPI` is raw HTTP
against `api.anthropic.com` with a pinned `anthropic-version` header rather than
the SDK.

On identity: the session holds `request.session["email"]` and nothing else. Tier
is resolved per request from (mode, identity) where mode is
`TEXT2SQL_DASHBOARD_MODE` and identity is matched against
`TEXT2SQL_JUDGE_ALLOWLIST` — both environment variables, both fixed until
restart. **There is no admin role and no user record anywhere in the package.**

## 1. One way to reach a model

**Goal.** One dispatch, one place, every call site: baseline, agentic, judge.

LiteLLM's value here is not "another provider". It is collapsing three
divergent tables into one, so a model string that works anywhere works
everywhere. That is the actual defect.

**Shape.** A single `resolve_client(model_name, params)` that every call site
uses. Keep the `provider:model` convention — it is embedded in `pipeline_id`, and
`pipeline_id` is the unit of comparison across the dashboard, summaries and
shareable links. Map the existing prefixes onto LiteLLM's names, keeping `wxai:`
as an alias so no stored artifact or judge YAML has to change.

**The hazard worth naming.** `pipeline_id` is derived from `model_name`
(`{model_name}-greedy-zero-shot-chatapi`). Any change to how a model is spelled
silently forks the id, and every stored artifact, alias and shared link keyed to
the old spelling stops matching. Whatever mapping we choose has to be
round-trippable, with a test asserting the ids generated for today's models are
byte-identical before and after.

**Do not** delete the hand-written clients in the same change. Route through
LiteLLM, keep the old path reachable behind a flag for one release, and compare
outputs on a test benchmark before removing 1,500-odd lines of working code.

**Worth taking while we are here.** LiteLLM knows per-model token costs, which is
what `estimate_cost_usd` and `TEXT2SQL_JUDGE_RATES` approximate by hand — and
`deployment.md` already warns those rates are estimates until calibrated against
an invoice. Sourcing them from LiteLLM removes a documented footgun.

**Done when:** the same model string works in all three call sites; judge configs
can name a non-watsonx model; `pipeline_id`s for existing models are unchanged;
the wxai path is covered by a test that does not need credentials.

## 2. Per-user API keys

This one changes the security posture of the whole deployment, and the plan
should be honest that it is the most expensive of the three.

**What it costs us.** `capability-tiers.md` currently claims, correctly:

> no profile is stored — the session holds a verified email address and nothing
> more, so signing out is clearing a cookie and there is no user database to secure

and separately, that a public deployment can hold **no credentials of any kind**,
so that even total failure of tier enforcement reaches nothing. Storing user API
keys ends both properties. There is then a database whose compromise hands an
attacker live billable credentials belonging to other people. That is a different
class of system from what is deployed today, and the docs must stop making the
old claim the moment this ships.

**If we do it, the non-negotiables:**

- **Encrypted at rest with a key held outside the database.** A master key from
  the environment, so the SQLite file alone is worthless. Follow the
  `JudgeStore` pattern (thread-local connections, schema constant in the module)
  but not its plaintext.
- **Write-only in the API.** No endpoint returns a stored key, ever — not
  masked, not truncated. The UI shows presence, a label, and last-used; nothing
  more. A "reveal" affordance is the thing that turns a leak into a breach.
- **Never logged.** The auth code already hashes identities before logging; keys
  need the same discipline, and a test that greps the log for a canary value.
- **Persistent until explicitly deleted.** Keys survive sign-out, as they do in
  every other service that stores credentials; re-pasting a key each visit would
  only push people to leave a session open forever, which is worse. The cost is
  that "signing out is clearing a cookie and nothing persists" stops being true,
  so that sentence must leave `capability-tiers.md` in the same release. The UI
  needs an obvious, always-available delete.
- **No user-supplied `base_url`.** LiteLLM will happily take one, and that turns
  the server into an open outbound proxy — the caller chooses the host, the
  server makes the request from inside the network. If custom endpoints are
  wanted, they belong in server config, not user input.

**Budgets: per-user caps, set from the console.** The server-held key keeps its
global monthly ceiling; each user additionally gets a cap an admin sets. This is
the most capable of the options considered and also the most build: it is a quota
subsystem, not a flag, and it should be scoped as such.

Two honesty constraints come with it. Metering a user's own key means reading
token usage back from every provider LiteLLM fronts, so this depends on item 1
landing first and on sourcing per-model costs from LiteLLM rather than the
hand-maintained `TEXT2SQL_JUDGE_RATES`. And a cap on someone else's key is only
enforceable *here* — we can refuse to make further calls from this server, but
the key still works everywhere else. The UI should say "your usage through this
dashboard", not "your usage", and every run must show which key will be billed
before it starts.

**Precondition.** Do not build this before item 3. "Who may store a key" is a
role question, and answering it with the current static allowlist means either
everyone signed in can, or only the judge allowlist can — neither is what is
wanted.

## 3. User management

**Goal.** An admin, bootstrapped from `.env`, grants roles to email addresses
from a console instead of a redeploy. Today changing the allowlist means editing
`deploy/.env` and `docker compose up -d --force-recreate app`.

**The tension to resolve before writing code.** The requested roles include
**full**. Full tier is SQL execution against configured database credentials,
registry writes, and evaluation runs — and the current design *refuses* to bind
full on a non-loopback interface without `--allow-remote-full`, precisely so it
cannot be reached over the internet. Granting full through a web console is
therefore not a new row in a table; it is a reversal of the deployment's central
safety property.

**Decided: the console may grant full, gated on `--allow-remote-full`.** The
mode ceiling still governs, so a database row can never carry a caller above what
the operator permitted at startup, and no new tier semantics are needed.

The practical shape of this: on a deployment started without the flag — which is
every deployment today, including the live one — the grant is *accepted and
inert*. An admin can mark someone full, and they stay capped at the ceiling until
an operator restarts with the flag. That must be visible, not silent: the console
should show such a grant as "full (not active on this deployment)" rather than
implying an access the server will refuse. A grant that looks effective and is
not is how people conclude the permission system is broken.

Rejected: capping the console at judge (cannot delegate SQL execution without
shell access), and splitting full into run-SQL and write-registry halves. The
split is probably the better end state and worth revisiting, but it means new
tier semantics, reclassifying every mutating route, and reworking the test that
enumerates them — too much to carry alongside the rest of 1.4.0.

**Invariants that must survive.** These are currently enforced by tests and
should stay that way:

- Mode remains a ceiling; no database row can raise a caller above it.
- Deny-by-default: a mutating route with no declared tier still requires full.
- The test enumerating every mutating route still passes.
- `email_verified` still gates everything — a role row keyed to an unverified
  address must not match.

**Bootstrapping.** The admin address comes from `.env`. Two failure modes to
design against explicitly: an unset variable must not mean "everyone is admin",
and it must not mean "nobody can ever administer" on a fresh database. Startup
should log the resolved admin count the way it already logs allowlist size, and
warn when it is zero.

**Migration: `TEXT2SQL_JUDGE_ALLOWLIST` is removed in 1.4.0.** Roles come only
from the database. One authority, no chance of two sources disagreeing — the
failure mode that is hardest to debug.

This is a breaking change, and it deletes the shell-level escape hatch, which
puts real weight on the admin bootstrap:

- **The admin variable becomes the only env-level authority**, and therefore the
  only recovery path. It must be re-read at every startup and must work against
  an empty or corrupt database — never "no admins because the table would not
  load". Log the resolved admin count the way allowlist size is logged today, and
  refuse to start, loudly, when a shared-mode deployment resolves zero.
- **Upgrading breaks judge access until the new variable is set.** Our own
  deployment currently grants judge through `TEXT2SQL_JUDGE_ALLOWLIST`; on
  upgrade that stops meaning anything and the tier is lost until the admin
  variable names an address and that admin grants roles. The release notes need
  the exact upgrade steps, and the startup warning should name the removed
  variable if it is still present in the environment — an operator who upgrades
  without reading the notes will otherwise see the allowlist silently do nothing.

## Sequencing

```
1. LiteLLM unification     independent, ship first
2. User management         establishes roles and the admin bootstrap
3. Per-user API keys       needs 2 for "who may", and 1 for per-model costs
```

Item 3's dependency on item 1 is stronger than it looks: per-user caps require
reading token usage back from whichever provider served the call, and unifying
that is exactly what item 1 does. Building the quota subsystem against three
divergent dispatch paths would mean writing it twice.

Item 1 is a refactor with a test-shaped definition of done. Items 2 and 3 both
touch authorization and should not be in flight at the same time.

Item 2 is the breaking one — it removes `TEXT2SQL_JUDGE_ALLOWLIST` — so it wants
its own release notes and a re-provisioning pass on the live deployment, not to
be folded into a larger drop.

## Decisions

Taken 2026-08-26. Recorded because each one closes off alternatives that will
look attractive again mid-implementation.

| Question | Decision |
|---|---|
| Full over the web | The console may grant it; it takes effect only where the operator started with `--allow-remote-full`. Inert grants must be shown as inert. |
| Whose budget | Per-user caps set by an admin, alongside the global ceiling on the server-held key. |
| Key lifetime | Persist until explicitly deleted. |
| Legacy allowlist | `TEXT2SQL_JUDGE_ALLOWLIST` removed; the database is the only authority. |

Two carry consequences that are easy to lose sight of later:

- **Per-user caps are a quota subsystem**, not a setting. They depend on item 1
  for per-model costs, and they can only ever bound spend *through this server*.
- **Removing the allowlist deletes the escape hatch.** The admin variable becomes
  the sole recovery path, so its failure modes are now everyone's failure modes.

## Still open

- **What the admin variable is called**, and whether it takes addresses or a
  domain. Naming it is trivial; deciding it takes a domain is not, since
  `@ibm.com` would make every colleague an admin on a public host.
- **Whether a user-supplied key may be used for batch inference**, or only for
  single-record judge runs. Batch turns a per-user cap into something that can be
  exhausted by one click, and the two have very different blast radii.
