# 1.4.0 — plan

Status: **all five items built and deployed** as of 2026-08-30, on branch
`1.4.0`, which has not yet been opened as a PR. Written 2026-08-26 against
`main` at 1.3.0; open questions resolved the same day (see *Decisions* at the
foot); progress tracked in *Status* immediately below.

Three things are wanted for 1.4.0:

1. **LiteLLM** as the way models are reached, alongside watsonx, plus OpenAI- and
   Anthropic-compatible endpoints wherever they are not already reachable.
2. **Per-user API keys entered in the UI**, stored as write-only secrets.
3. **A user management console** where an admin — an email named in `.env` — grants
   other addresses admin / full / judge / read-only.

Two more come **before** any of them — documentation and tests — because they are
what makes the rest safe to attempt.

## The standing requirement

**The pip-installable surface does not change because of dashboard work.** The
library functions, the CLI and the notebook paths are a published contract: they
are on PyPI, other people import them, and none of the three features above is a
reason to alter a signature, a return shape or a default.

Dashboard features live in `ui/`. Where one genuinely needs something from the
library — per-user credentials are the only case here — the library gains an
*optional* parameter that defaults to today's behaviour, and nothing else. Any
change that makes an existing caller behave differently is out of scope for
1.4.0, whatever it would buy the dashboard.

This is a requirement rather than a preference, and *Test coverage* below is how
it stops being an aspiration.

They are ordered deliberately. (1) is self-contained and pays off immediately.
(2) and (3) both change what the server persists about people, and (2) is much
safer to build once (3) exists to say who may do it.

## What is actually there today

Worth stating precisely, because the current state is less uniform than
`CLAUDE.md` implies. Three call sites each dispatch on the model-name prefix, and
**each supports a different set**:

| Call site | Accepts |
|---|---|
| [`agentic_pipeline._create_llm_client`](../../../src/text2sql_eval_toolkit/inference/agentic_pipeline.py#L356) | `wxai:` `gemini:` `anthropic:` `vllm:` `openai:` `rits` |
| [`baseline_llm_pipeline`](../../../src/text2sql_eval_toolkit/inference/baseline_llm_pipeline.py#L78) | `wxai:` `gemini:` `vllm:` |
| [`llm_as_judge`](../../../src/text2sql_eval_toolkit/evaluation/llm_as_judge.py#L85) | `wxai:` only |

So `anthropic:claude-...` runs an agentic pipeline and raises `NotImplementedError`
on the baseline; no judge config can name anything but watsonx. The answer to
"is OpenAI/Claude already supported" is *partly, in one of three places*.

Behind those prefixes are six hand-written clients in `inference_tools.py` —
`WXAIClient`, `WXAIClientChatAPI`, `VLLMClientChatAPI`, `ClaudeClientChatAPI`,
`OpenAIClientChatAPI`, `GeminiClientChatAPI`. `ClaudeClientChatAPI` is raw HTTP
against `api.anthropic.com` with a pinned `anthropic-version` header rather than
the SDK.

On identity: the session holds `request.session["email"]` and nothing else. Tier
is resolved per request from (mode, identity) where mode is
`TEXT2SQL_DASHBOARD_MODE` and identity is matched against
`TEXT2SQL_JUDGE_ALLOWLIST` — both environment variables, both fixed until
restart. **There is no admin role and no user record anywhere in the package.**

## Documentation

**Where it stands.** 25 of the 41 symbols exported from `__init__` have **no
docstring at all**, and 3 more are a single line. Only 13 are properly documented.
Meanwhile [`README.md:237`](../../../README.md#L237) tells readers:

> See the docstrings of the exported functions/classes in
> `text2sql_eval_toolkit.__init__` for the full list of public APIs.

That is a promise the package does not keep for most of its own public surface,
made on the page PyPI renders as the project's front door.

**What to build.** Docstrings first, on all 41 exported symbols — Google style,
as the rest of the codebase already uses, with the arguments, the return shape,
and at least one worked example for anything a user would call directly. The
existing 13 are the model.

Then a generated API reference. Google-style docstrings mean Sphinx with
`napoleon`, or mkdocs with `mkdocstrings`; either is fine and neither needs the
docstrings to be written twice.

**On "docs on PyPI".** Worth being precise, because PyPI does not host API
documentation. It renders `README.md` as the project page — that already
works — and it shows entries from `[project.urls]` in the sidebar, which today
contains only `Homepage`. So the shape of this is: host the generated reference
(Read the Docs or GitHub Pages), then add `Documentation` and `Changelog` to
`[project.urls]` so PyPI links them prominently. The README stays the landing
page and should gain a short "full API reference" link rather than growing.

**Done when:** every exported symbol has a docstring; the reference builds in CI
and fails the build on a broken reference; PyPI's sidebar links it.

**Done, with one caveat.** All 43 exports carry a docstring (41 at planning time;
the surface grew by two). mkdocs with `mkdocstrings`, reference under
`docs/reference/`, `mkdocs build --strict` in CI, and `Documentation` and
`Changelog` added to `[project.urls]`. Writing the docstrings turned up **five
real defects** in the process of describing what the functions did — the
documentation pass paid for itself before the reference was published.

The caveat: `.github/workflows/docs.yml` publishes only on push to `main`, so
`https://ibm.github.io/text2sql-eval-toolkit/` **currently 404s** — and that is
the URL `[project.urls]` already advertises. It resolves when this branch
merges, provided Pages is set to "GitHub Actions" as a one-time repository
setting. Releasing before either happens would put a dead link in PyPI's
sidebar.

## One way to reach a model

**Goal.** One dispatch, one place, every call site: baseline, agentic, judge.

LiteLLM's value here is not "another provider". It is collapsing three
divergent tables into one, so a model string that works anywhere works
everywhere. That is the actual defect.

**Shape.** A single `resolve_client(model_name, params, *, api_key=None,
on_usage=None)` that every call site uses. The two optional parameters exist from
the start rather than being retrofitted: they are what lets *Per-user API keys* meter a
per-user key without putting quota logic in the library (see *The quota stays out
of the library*). Omitted, they mean "read the environment", which is what every
library and CLI caller does. Keep the `provider:model` convention — it is embedded in `pipeline_id`, and
`pipeline_id` is the unit of comparison across the dashboard, summaries and
shareable links. Map the existing prefixes onto LiteLLM's names, keeping `wxai:`
as an alias so no stored artifact or judge YAML has to change.

**The hazard worth naming.** `pipeline_id` is derived from `model_name`
(`{model_name}-greedy-zero-shot-chatapi`). Any change to how a model is spelled
silently forks the id, and every stored artifact, alias and shared link keyed to
the old spelling stops matching. Whatever mapping we choose has to be
round-trippable, with a test asserting the ids generated for today's models are
byte-identical before and after.

**Do not** delete the hand-written clients in the same change. Route through
LiteLLM, keep the old path reachable behind a flag for one release, and compare
outputs on a test benchmark before removing 1,500-odd lines of working code.

**Worth taking while we are here.** LiteLLM knows per-model token costs, which is
what `estimate_cost_usd` and `TEXT2SQL_JUDGE_RATES` approximate by hand — and
`deployment.md` already warns those rates are estimates until calibrated against
an invoice. Sourcing them from LiteLLM removes a documented footgun.

**Done when:** the same model string works in all three call sites; judge configs
can name a non-watsonx model; `pipeline_id`s for existing models are unchanged;
the wxai path is covered by a test that does not need credentials.

**Done.** `inference/model_clients.py` holds the single `NATIVE_PREFIXES` table —
`wxai:`, `gemini:`, `anthropic:`, `openai:`, `vllm:`, `ollama:` — with `litellm:`
appended when the optional extra is installed. Client classes are resolved *by
name* at call time, which keeps the table importable regardless of import order
and makes it testable without credentials.

Verified against real providers: watsonx and Anthropic both return substantive
verdicts through a judge config. OpenAI, Gemini and `litellm:` are covered by
tests but have not been called for real.

## Per-user API keys

This one changes the security posture of the whole deployment, and the plan
should be honest that it is the most expensive of the three.

**What it costs us.** `capability-tiers.md` currently claims, correctly:

> no profile is stored — the session holds a verified email address and nothing
> more, so signing out is clearing a cookie and there is no user database to secure

and separately, that a public deployment can hold **no credentials of any kind**,
so that even total failure of tier enforcement reaches nothing. Storing user API
keys ends both properties. There is then a database whose compromise hands an
attacker live billable credentials belonging to other people. That is a different
class of system from what is deployed today, and the docs must stop making the
old claim the moment this ships.

**If we do it, the non-negotiables:**

- **Encrypted at rest with a key held outside the database.** A master key from
  the environment, so the SQLite file alone is worthless. Follow the
  `JudgeStore` pattern (thread-local connections, schema constant in the module)
  but not its plaintext.
- **Write-only in the API.** No endpoint returns a stored key, ever — not
  masked, not truncated. The UI shows presence, a label, and last-used; nothing
  more. A "reveal" affordance is the thing that turns a leak into a breach.
- **Never logged.** The auth code already hashes identities before logging; keys
  need the same discipline, and a test that greps the log for a canary value.
- **Persistent until explicitly deleted.** Keys survive sign-out, as they do in
  every other service that stores credentials; re-pasting a key each visit would
  only push people to leave a session open forever, which is worse. The cost is
  that "signing out is clearing a cookie and nothing persists" stops being true,
  so that sentence must leave `capability-tiers.md` in the same release. The UI
  needs an obvious, always-available delete.
- **No user-supplied `base_url`.** LiteLLM will happily take one, and that turns
  the server into an open outbound proxy — the caller chooses the host, the
  server makes the request from inside the network. If custom endpoints are
  wanted, they belong in server config, not user input.

**Budgets: per-user caps, set from the console.** The server-held key keeps its
global monthly ceiling; each user additionally gets a cap an admin sets. This is
the most capable of the options considered and also the most build: it is a quota
subsystem, not a flag, and it should be scoped as such.

Two honesty constraints come with it. Metering a user's own key means reading
token usage back from every provider LiteLLM fronts, so this depends on
*One way to reach a model* landing first and on sourcing per-model costs from LiteLLM rather than the
hand-maintained `TEXT2SQL_JUDGE_RATES`. And a cap on someone else's key is only
enforceable *here* — we can refuse to make further calls from this server, but
the key still works everywhere else. The UI should say "your usage through this
dashboard", not "your usage", and every run must show which key will be billed
before it starts.

**What a user key may drive: anything.** Judge runs, baseline inference, agentic
pipelines, batch evaluations. The rule that keeps this coherent is a separation
worth stating once and applying everywhere: **tier governs who may start a
workload; the key governs whose account pays for it.** Opening batch inference to
a user's key does not open batch inference to a lower tier.

That separation matters because the job registry assumes otherwise today.
[`jobs.py`](../../../src/text2sql_eval_toolkit/ui/jobs.py) is a dict behind a
lock, and says so deliberately — "single-operator state", no user attribution,
would not survive a second replica, and the public host runs no jobs at all. A
full-tier operator running a batch billed to their own stored key needs none of
that to change. Ever letting a lower tier *start* a batch does: jobs would need
an owner, per-user isolation, and a story for two replicas. Keep those separable,
and do not let the second arrive by accident.

**Enforcing a cap under concurrency.** Batch evaluation runs with
`asyncio.Semaphore(max_concurrency)`, default 16. A naive check-then-spend
therefore overshoots by up to fifteen calls: sixteen coroutines each read a cap
that is still under budget, then all sixteen spend. Reserve before the call and
reconcile after it with the real token counts, so the in-flight amount is visible
to every other coroutine. The same reasoning applies to the ledger write, which
must be durable per call — a batch that crashes at record 900 must not forget
what the first 899 cost.

Enforcement also has to be **mid-run, not pre-flight**. Checking once at the top
of a 1,034-record benchmark and then spending freely makes the cap decorative.
Show an estimate before starting, stop cleanly when the cap is reached, and
report what was completed rather than failing the whole job.

**The quota stays out of the library.** Metering is a UI concern: the toolkit's
library functions, CLI and notebooks must behave exactly as they do now, with no
user, no cap and no ledger anywhere in their path. That is achievable, but not
for free, because of where credentials are read today.

All six clients in `inference_tools.py` take `(model_name, model_parameters)` and
fetch their credential from `os.environ` inside `__init__` — `ANTHROPIC_API_KEY`,
`GEMINI_API_KEY`, and so on. Nothing can be passed in. So the UI has no way to
say "use *this* user's key for *this* call".

**Do not solve that by setting environment variables around the call.** `os.environ`
is process-global and batch work runs sixteen coroutines against one semaphore,
so concurrent runs by two users would race and one person's key would serve the
other's request — wrong billing at best, credential leakage between accounts at
worst. This is the tempting shortcut and it must be written off explicitly.

The seam that does work is small and additive:

- Client constructors and the entry points that build them take an **optional**
  credential and an **optional** `on_usage` callback. Omitted — which is every
  library, CLI and notebook call — they read the environment exactly as today.
- The UI passes both: the caller's decrypted key, and a callback that reconciles
  reserved budget against real token counts.
- **The library never imports the ledger.** It exposes a hook; the UI supplies
  the policy. Quota, caps, reservation and refusal live entirely in `ui/`.

Two consequences to plan for. The seam has to reach every entry point the UI
calls, not just the client classes — `evaluate_sql_prediction_with_llm` builds
its client from YAML internally, and the batch entry points build theirs deeper
still, so the parameter has to thread down through each. And this is exactly the
plumbing *One way to reach a model* is already touching: `resolve_client` should be born with these
parameters rather than have them retrofitted a release later.

**Done when:** the CLI and library paths are byte-identical with the feature
present — a test asserting a library call with no credential argument still reads
the environment and never touches the quota store.

**Done.** `ui/user_keys.py`, Fernet-encrypted under a master key from
`TEXT2SQL_SECRET_KEY`, with reserve-then-reconcile spend caps that hold under the
bounded concurrency the execution layer already uses. Credentials are revealed
only for the duration of one request. The library path is untouched: the clients
gained an optional `api_key` that defaults to the same environment lookup as
before.

**Precondition.** Do not build this before *User management*. "Who may store a key" is a
role question, and answering it with the current static allowlist means either
everyone signed in can, or only the judge allowlist can — neither is what is
wanted.

## User management

**Goal.** An admin, bootstrapped from `.env`, grants roles to email addresses
from a console instead of a redeploy. Today changing the allowlist means editing
`deploy/.env` and `docker compose up -d --force-recreate app`.

**The tension to resolve before writing code.** The requested roles include
**full**. Full tier is SQL execution against configured database credentials,
registry writes, and evaluation runs — and the current design *refuses* to bind
full on a non-loopback interface without `--allow-remote-full`, precisely so it
cannot be reached over the internet. Granting full through a web console is
therefore not a new row in a table; it is a reversal of the deployment's central
safety property.

**Decided: the console may grant full, gated on `--allow-remote-full`.** The
mode ceiling still governs, so a database row can never carry a caller above what
the operator permitted at startup, and no new tier semantics are needed.

The practical shape of this: on a deployment started without the flag — which is
every deployment today, including the live one — the grant is *accepted and
inert*. An admin can mark someone full, and they stay capped at the ceiling until
an operator restarts with the flag. That must be visible, not silent: the console
should show such a grant as "full (not active on this deployment)" rather than
implying an access the server will refuse. A grant that looks effective and is
not is how people conclude the permission system is broken.

Rejected: capping the console at judge (cannot delegate SQL execution without
shell access), and splitting full into run-SQL and write-registry halves. The
split is probably the better end state and worth revisiting, but it means new
tier semantics, reclassifying every mutating route, and reworking the test that
enumerates them — too much to carry alongside the rest of 1.4.0.

**Invariants that must survive.** These are currently enforced by tests and
should stay that way:

- Mode remains a ceiling; no database row can raise a caller above it.
- Deny-by-default: a mutating route with no declared tier still requires full.
- The test enumerating every mutating route still passes.
- `email_verified` still gates everything — a role row keyed to an unverified
  address must not match.

**Bootstrapping: `TEXT2SQL_ADMIN_EMAILS`.** It holds **email addresses, not
domains**, and
an address is matched against the Google-verified login email for that user. A
domain would have been cheaper to administer and is the wrong tool here: `@ibm.com`
would make every colleague an admin of a host on the public internet.

Reuse the existing normalisation rather than inventing one —
[`parse_allowlist`](../../../src/text2sql_eval_toolkit/ui/capabilities.py#L179)
splits on commas and applies `.strip().lower()`, and the match side lowercases
the session email the same way. Following it exactly means the admin variable
behaves like the allowlist operators already know, and an address that worked in
one works in the other.

The failure mode to design for is a typo that locks everyone out: the address in
`.env` must be *exactly* what Google returns as the `email` claim. Gmail's dot
and `+tag` variants deliver to the same inbox but are different strings, and the
claim carries only the canonical form. Startup should log the resolved admin
count — and, at debug level, the hashed identities the way auth already hashes
them — so a mismatch is diagnosable without printing anyone's address to a log. Two failure modes to
design against explicitly: an unset variable must not mean "everyone is admin",
and it must not mean "nobody can ever administer" on a fresh database. Startup
should log the resolved admin count the way it already logs allowlist size, and
warn when it is zero.

**Migration: `TEXT2SQL_JUDGE_ALLOWLIST` is removed in 1.4.0.** Roles come only
from the database. One authority, no chance of two sources disagreeing — the
failure mode that is hardest to debug.

This is a breaking change, and it deletes the shell-level escape hatch, which
puts real weight on the admin bootstrap:

- **`TEXT2SQL_ADMIN_EMAILS` becomes the only env-level authority**, and therefore
  the only recovery path. It is *not* a one-time seed: it is read at every
  startup and always grants admin, so an operator with shell access can always
  recover a deployment whose role table is wrong. It must work against
  an empty or corrupt database — never "no admins because the table would not
  load". Log the resolved admin count the way allowlist size is logged today, and
  refuse to start, loudly, when a shared-mode deployment resolves zero.
- **Upgrading breaks judge access until the new variable is set.** Our own
  deployment currently grants judge through `TEXT2SQL_JUDGE_ALLOWLIST`; on
  upgrade that stops meaning anything and the tier is lost until the admin
  variable names an address and that admin grants roles. The release notes need
  the exact upgrade steps, and the startup warning should name the removed
  variable if it is still present in the environment — an operator who upgrades
  without reading the notes will otherwise see the allowlist silently do nothing.

**Done.** `ui/roles.py` holds the `Role` enum, the role→tier map and a SQLite
`UserStore`; the Users console grants and revokes from the dashboard.
`TEXT2SQL_ADMIN_EMAILS` is read every startup and always wins over the table, so
it stays a recovery path rather than a one-time seed. Admin is a gate
*orthogonal* to tier — an admin must be able to grant roles on a judge-mode host,
which a `FULL` tier requirement would have denied.

The release notes for the `TEXT2SQL_JUDGE_ALLOWLIST` removal are **not written
yet**; see *Still open*.

## Work not in the original plan

Everything here was found by deploying the thing and then using it. None of it
was visible from reading the code, which is the point worth keeping.

### The deployment could only ever have used watsonx

The plan's premise was that unifying the dispatch tables would make every
provider reachable. It did — in the library. The *deployment* still could not
use any of them, because `deploy/docker-compose.yml` passed only the watsonx
variables into the container. A judge config naming `anthropic:` would resolve,
build a client, and then fail on a credential the container had never been
given. Fixed by passing `ANTHROPIC_API_KEY`, `ANTHROPIC_WORKSPACE_ID`,
`OPENAI_API_KEY` and `GEMINI_API_KEY` through compose.

### Three defects that only appear when a judge actually runs

Unifying the dispatch tables routed the judge through a chat client for the
first time. All three of these were invisible to the test suite, which had never
called a real provider:

1. **The judge's prompt is a bare string**, and the chat clients accept only a
   message list — every run failed with "Incorrect prompt type". Introduced by
   the unification.
2. **The Claude client printed its entire request payload to stdout** — prompt,
   question, ground truth — into the container logs on every call.
3. **The judge was being told to write SQL.** The Claude client sent "You are a
   SQL expert… convert natural language questions into accurate SQL queries" as
   the system message on *every* request, judging included. A contradiction the
   model has to resolve, and a quiet bias on verdicts. Now sent only when the
   caller wants SQL.

### `WATSONX_PROJECTID` versus `WATSONX_PROJECT_ID`

The toolkit's spelling has no underscore before `ID`; IBM's own documentation
mostly writes the underscored form. Setting the sensible-looking one produced
`Missing WATSONX.AI credentials … WATSONX_PROJECTID` while a near-identically
named variable sat unread in the same file. Both spellings are now accepted for
all three watsonx variables, and the error names every accepted spelling —
"set `WATSONX_PROJECTID`" is unhelpful advice to someone who already did.

### Judge configs were written into `site-packages`

`PUT /api/llm-judge/configs/{name}` wrote YAML into the installed package
directory. On the deployment that tree is root-owned and the server runs
unprivileged, so every save returned a bare 500. The location was wrong
regardless of permissions: a pip upgrade discards the edit.

Writes now land in `<data root>/llm_judge_config` and *shadow* the packaged
config of the same name; deleting the copy uncovers the original, which is the
way back from an edit that broke a shipped config. The editor also had no way to
**create** a config — only to overwrite the selected one — so the first attempt
to add a Claude judge was on course to overwrite the shipped default.

### A Judge Playground, and sharing what it says

Running the judge produced a verdict that existed in one browser tab only: the
address did not change, and the exports omitted it. The address now carries
`?judge=<config>` once a verdict is on screen, and opening such a link restores
it.

The subtlety is that restoring must be **cached-only** — a new flag on the judge
endpoint returning 204 when nothing is stored. Opening a link someone sent must
not start an inference: the sender is sharing an answer, not authorising the
reader to spend against the budget or against their own provider key. A
consequence worth keeping: an exhausted budget still serves a shared link rather
than turning it into a 429.

The URL names the config rather than embedding the verdict. The verdict is
cached against the record, pipeline and config *contents*, so the name brings
back the same answer, and a URL cannot be edited into claiming a verdict the
judge never gave.

### The exports had never carried the stored judge explanation

Separate from the above, and older: `llm_explanation` from the published
evaluation is rendered as prose rather than as a metric row, and the export only
ever walked the metric rows. It had therefore been absent from **every** export
since exports existed — including before the Judge Playground was built.

### Dashboard addressability and navigation

- The Eval Playground had no URL state; it is now addressable by benchmark,
  record and pipeline.
- Export of a playground record as URL / Markdown / HTML, as an icon action.
  There is no PDF writer: a real one is a ~300 KB dependency against a 460 KB
  entry-bundle budget, to reproduce what every browser's print dialog does.
- Benchmarks became a page in the nav with its own URL rather than a slide-out
  panel, and every nav item became a real link — so right-click, Open in new
  window works.
- A sign-out button when signed in.

### Deployment and data

- The public URL moved to `text2sql-eval-toolkit.oaklayer.dev`.
- `full` mode enabled remotely, with SQLite, Postgres and MySQL databases copied
  over; all six benchmarks execute on the server.
- The container had results but **no benchmark definitions** — `results fetch`
  downloads `results/**` and nothing else. Seeded from the image.
- MySQL was configured with `mysql+pymysql://`, which the asyncio engine
  refuses; a sync driver in the connection string is now translated.
- The playground loaded a hardcoded record id it knew was absent; it now falls
  back to the first record.

### Two security findings worth recording

- **`resolve_tier` would have granted `full` to anonymous internet users.** The
  short-circuit that returns `FULL` when the server is in full mode ran before
  the identity check. Caught before enabling full mode remotely; the fix adds a
  `remote` flag, and anonymous callers on the full-mode host now resolve to
  `public` and get 403 on `/execute`, `/api/users` and `/evaluate`.
- **`SessionBar` hid the whole strip on a remote-full deployment**, so a
  signed-in user had no sign-out. The first fix was too broad and three existing
  tests caught it — which is the test coverage item doing its job.

## Sequencing

```
1. Documentation          docstrings on all 41 exports, generated reference
2. Test coverage          characterisation tests over the public API
   -- the guardrail; everything below changes code these two now protect --
3. LiteLLM unification    independent of 4 and 5, ship first of the three
4. User management        establishes roles and the admin bootstrap
5. Per-user API keys      needs 4 for "who may", and 3 for per-model costs
```

Documentation and tests come first for a reason that is not tidiness. The
standing requirement — that the pip-installable surface does not change — is
unenforceable until something enforces it. Written after the refactors, the
characterisation tests would encode whatever behaviour those refactors happened
to produce, including any accident. Written before, they fail when it changes.

The dependency of *Per-user API keys* on *One way to reach a model* is stronger
than it looks: per-user caps require
reading token usage back from whichever provider served the call, and unifying
that is exactly what *One way to reach a model* does. Building the quota subsystem against three
divergent dispatch paths would mean writing it twice.

Item 1 is a refactor with a test-shaped definition of done. Items 2 and 3 both
touch authorization and should not be in flight at the same time.

Item 2 is the breaking one — it removes `TEXT2SQL_JUDGE_ALLOWLIST` — so it wants
its own release notes and a re-provisioning pass on the live deployment, not to
be folded into a larger drop.

## Decisions

Taken 2026-08-26. Recorded because each one closes off alternatives that will
look attractive again mid-implementation.

| Question | Decision |
|---|---|
| Full over the web | The console may grant it; it takes effect only where the operator started with `--allow-remote-full`. Inert grants must be shown as inert. |
| Whose budget | Per-user caps set by an admin, alongside the global ceiling on the server-held key. |
| Key lifetime | Persist until explicitly deleted. |
| Legacy allowlist | `TEXT2SQL_JUDGE_ALLOWLIST` removed; the database is the only authority. |
| Admin bootstrap | `TEXT2SQL_ADMIN_EMAILS`: addresses, not domains, matched against the verified login email and normalised like the existing allowlist. Read every startup, always grants admin — the standing recovery path, not a one-time seed. |
| User-key scope | Any workload. Tier still governs who may start one; the key only decides who pays. |
| Library stability | The pip-installable surface does not change because of dashboard work. Optional parameters defaulting to today's behaviour are the only permitted addition. |
| Where the quota lives | UI only. Library, CLI and notebook paths are unchanged and never touch it; clients gain optional credential and usage-callback parameters that default to today's environment lookup. |

Two carry consequences that are easy to lose sight of later:

- **Per-user caps are a quota subsystem**, not a setting. They depend on
  *One way to reach a model* for per-model costs, and they can only ever bound spend *through this server*.
- **Removing the allowlist deletes the escape hatch.** The admin variable becomes
  the sole recovery path, so its failure modes are now everyone's failure modes.

## Still open

No open questions. What remains is release mechanics and two verification gaps:

- **The version is still `1.3.0`** in `pyproject.toml`, and branch `1.4.0` has
  never been opened as a PR. The bump, the changelog, the PR and the tag-driven
  PyPI publish are the remaining work.
- **The documentation URL in `[project.urls]` 404s today.** Pages publishes on
  push to `main` only, and needs its source set to "GitHub Actions" once in
  repository settings. Both must be true before a release, or PyPI's sidebar
  advertises a dead link.
- **`TEXT2SQL_JUDGE_ALLOWLIST` removal needs release notes.** The plan flagged
  this as the breaking change wanting its own re-provisioning pass; that note is
  not written yet.
- **Only the watsonx and Anthropic judge paths have been exercised against a
  real provider.** OpenAI, Gemini and the `litellm:` prefix are covered by tests
  and by the shared dispatch table, but nothing has actually called them.
- **No packaged judge config names a non-watsonx model**, so Claude is not
  selectable from the Judge Playground dropdown without first creating a config.

The two risks the plan called out both materialised, and both cost roughly what
it predicted. The quota subsystem in *Per-user API keys* was the largest single
piece of the branch. The loss of the shell-level escape hatch in *User
management* has not bitten, but `TEXT2SQL_ADMIN_EMAILS` is now genuinely the only
recovery path, and it is one typo away from locking the operator out of their own
console.
