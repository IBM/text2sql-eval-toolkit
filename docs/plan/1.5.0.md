# 1.5.0 — plan

Status: written 2026-08-31 against `main` at 1.4.0, nothing implemented.

Four items, in the order they should be done:

1. **Dependency vulnerabilities** — 158 open Dependabot alerts, and a second
   dependency manifest that has no business existing.
2. **Release automation** — the tag, the PyPI publish and the GitHub Release
   should come from one push. Today the Release page is created by hand, and has
   been forgotten twice.
3. **A docs view in the dashboard** — the published reference plus
   locally-authored Markdown, for use in a demo.
4. **A usable judge-config editor** — JSON syntax highlighting and reformatting,
   so editing a config stops being an exercise in counting braces.

(1) first because it is the only one with a clock on it. (2) next because it is
small and every subsequent release benefits. (3) is the largest. (4) is small and
independent; it shares the bundle-budget constraint with (3), so decide that
once and apply it to both.

## The standing requirement, still

**The pip-installable surface does not change because of dashboard work.** It is
in `CONTRIBUTING.md` now rather than in a plan document, which is where it
belongs — but item 3 is dashboard work that will want to reach into the package
for content, so it is worth restating here. `tests/test_public_api.py` and the
characterisation suite are what enforce it.

## 1. Dependency vulnerabilities

**Where it stands.** 158 open alerts: 1 critical, 87 high, 61 medium, 9 low.
They resolve to **28 distinct packages** across three manifests:

| Manifest | Alerts | What it is |
|---|---|---|
| `uv.lock` | 102 | The real lockfile |
| `requirements.txt` | 50 | A pinned freeze that is **not** the source of truth |
| `dashboard/package-lock.json` | 6 | `vite`, `postcss` |

The alert count overstates the work: many packages carry several advisories, and
the same package is counted once per manifest it appears in.

**The split that matters.** Of the 28 packages, only 15 are in the base install
— what someone gets from `pip install text2sql-eval-toolkit`:

> `cryptography`, `idna`, `langchain-core`, `langgraph`, `langgraph-checkpoint`,
> `langgraph-sdk`, `langsmith`, `orjson`, `pillow`, `pyasn1`, `python-dotenv`,
> `requests`, `setuptools`, `sqlparse`, `urllib3`

The other 13 reach users only through an extra or the dev toolchain:
`bleach`, `immutable`, `jupyter-server`, `jupyterlab`, `mistune`, `nbconvert`,
`notebook`, `postcss`, `pygments`, `soupsieve`, `starlette`, `tornado`, `vite`.

The **one critical** alert — a stored XSS in Jupyter Server's nbconvert handlers,
fixed in 2.20.0 — is in that second group, pulled in by the `notebook` extra. It
is real, but it does not reach anyone who installs the toolkit normally, and it
is not a vulnerability in this project's own code.

`cryptography` is the one to look at first regardless of severity ordering: it is
in the base install and it is what encrypts stored per-user provider keys.

**What to build.**

- Raise the floors in `pyproject.toml` for the 15 base packages to their first
  patched versions, relock, and confirm nothing in the resolution moves that
  should not.
- **Delete `requirements.txt`.** It is a pinned freeze that already disagrees
  with `pyproject.toml` — it carries `datasets`, `evaluate` and `aiohttp`, which
  are not dependencies of this project — and CI has a job whose whole purpose is
  keeping it in sync with `uv.lock`. Two sources of truth, 50 alerts, and a CI
  job to paper over the gap. `uv.lock` and `pyproject.toml` are enough; anyone
  wanting a pinned file can `uv export`. This alone removes about a third of the
  alerts without changing a single dependency.
- Bump the frontend's `vite` and `postcss`, which is a lockfile change and a
  rebuild.
- Decide on the `notebook` extra. The critical alert and most of the high ones
  arrive through it, for two notebooks. Either pin it forward to a jupyter stack
  that is clean, or drop the extra and document `pip install jupyter` — the
  toolkit does not import jupyter, it only ships notebooks that need it.
- Turn on Dependabot version updates for `uv.lock` and `dashboard/`, so this
  stops accumulating between releases.

**Done when:** no open alert names a package in the base install; the critical
alert is resolved or explicitly dismissed with a reason; `requirements.txt` is
gone along with the CI job that guarded it; the full suite and the container
smoke test still pass.

**Watch for:** `langgraph` and `langchain-core` are the agentic pipeline's spine,
and their minor releases move fast. Bump them deliberately and run the agentic
tests, rather than taking whatever the resolver offers.

## 2. The GitHub Release should come from the tag

**Where it stands.** `release.yml` has two jobs: `build` (build, verify the tag
matches the packaged version, check the wheel carries its UI and judge configs,
`twine check`) and `publish` (Trusted Publishing to PyPI, gated on the `pypi`
environment). Neither creates a GitHub Release.

So a release is: push a tag → wait → approve the environment → *and then
separately remember to write the Release page by hand*. That last step has been
missed on both 1.3.0 and 1.4.0. It is the step a human forgets because nothing
fails when they do.

**What to build.** A third job, after `publish` succeeds, that creates the
Release from the changelog:

- Extract the section for the tag's version from `CHANGELOG.md`. This is worth a
  small script under `scripts/ci/` rather than shell inside the YAML, because it
  is the kind of thing that should have a test: a tag with no matching changelog
  section must **fail the release**, not publish an empty page.
- Create the Release with `gh release create --verify-tag`, attaching the built
  wheel and sdist from the `dist` artifact the build job already uploads.
- The job needs `contents: write`; nothing else. Keep it as narrow as the
  publish job's `id-token: write`.
- Order it after `publish`, not in parallel. A Release page pointing at a
  version PyPI rejected is worse than a missing one.

**Done when:** pushing a tag produces the PyPI release *and* the GitHub Release
with the changelog notes, with no manual step; and a tag whose version has no
changelog section fails the workflow with a message saying so.

## 3. A docs view in the dashboard

**The goal.** A place in the dashboard to read documentation — the published
reference at <https://text2sql-eval-toolkit.readthedocs.io/en/latest/>, plus
Markdown authored for this project that does not belong on the API reference
site: a survey of the state of the art in text-to-SQL evaluation, worked
examples, and the insights worth showing in a demo.

**Where it stands.** Nothing exists. Views are lazy-loaded components in
`dashboard/src/views/`, routed by `parseLocation` in `dashboard/src/lib/routes.ts`
and dispatched in `dashboard/src/pages/App.tsx`; every nav item is a real link.
There is **no Markdown renderer in the frontend** and none server-side either.

**The constraint that shapes this.** The entry bundle is **418 KB against a
460 KB budget** enforced in CI — 42 KB of headroom. A Markdown renderer and a
syntax highlighter do not fit there. So either the view is lazy-loaded and pulls
its renderer into its own chunk (the existing views are already lazy, so this is
the natural fit), or Markdown is rendered to HTML server-side and the view
displays it. Decide this before writing any of it.

**Two halves, and they are not the same problem.**

*The published reference.* Embedding another origin in an iframe is the cheap
answer and a poor one: the dashboard sets `X-Frame-Options: DENY` and a
restrictive CSP on its own responses, Read the Docs sets its own headers, and a
framed site inside a tool with a session cookie is a thing to think about rather
than assume. The honest options are to link out prominently, or to build the
mkdocs site into the image and serve it under `/docs` from the same origin —
which also makes the dashboard's docs work offline, matching how the dashboard
already ships its own frontend in the wheel.

*The authored Markdown.* Files like `state-of-the-art.md`. Open question below
on where they live. These need rendering, and they are the half that matters for
a demo.

**Decided.** The four questions this section opened with are answered, and the
answers narrow it considerably:

| Question | Decision |
|---|---|
| Where do documents live | In `docs/`, versioned with the code. No data-root overlay. |
| Is the view editable | **No.** Read-only. |
| Published reference | Embedded from Read the Docs. |
| Ship demo content to PyPI | **No.** It stays in the repository, public on GitHub. |

Two of these have consequences that are not obvious from the decision itself.

**`docs/` ships in neither the wheel nor the sdist** — verified, zero files in
both. That is exactly what the fourth decision asks for, so no packaging change
is needed. The consequence is that **the docs view is empty for anyone who
installed from PyPI**: the files are not there to read. That is acceptable
because the demo runs from a branch checkout on the server, where they are — but
the view must say so plainly rather than rendering a blank page or a 500. "No
documents are installed; this view reads them from the repository" is the
correct empty state.

**A cross-origin iframe cannot be restyled from the page that frames it.** The
same-origin policy forbids reaching into it, so "style it like the dashboard"
is not achievable *in the frame* however it is approached. What is achievable,
and gets the same result, is theming the mkdocs site itself — `mkdocs-material`
takes a palette, and pointing it at Carbon's colours makes the docs match the
dashboard everywhere, including for people who visit Read the Docs directly.
That is the version worth doing, and it is cheaper than any iframe trickery.

**Embedding is permitted, but our own policy currently forbids it.** Read the
Docs sends no `X-Frame-Options` and no `frame-ancestors`, so it consents to
being framed. The blocker is on our side: the dashboard's CSP sets
`default-src 'self'` and declares no `frame-src`, and `frame-src` falls back to
`default-src` — so the browser blocks the iframe. It needs

```
frame-src https://text2sql-eval-toolkit.readthedocs.io;
```

named explicitly, never a wildcard.

Worth being precise, because these are easy to conflate: the
`X-Frame-Options: DENY` and `frame-ancestors 'none'` the dashboard already sends
govern *the dashboard being framed by someone else*. They are unrelated to the
dashboard framing another site, and they should stay exactly as they are.

**What to build.**

- A `docs` view with its own route, in the nav like every other page, addressable
  so a specific document can be linked — `/docs/state-of-the-art` and not just
  `/docs`. Sharing a link to the exact thing being discussed is the whole point
  in a demo.
- A read-only server endpoint listing the available documents and returning one
  by name. It must validate the name the way `_resolve_judge_config_path` does —
  a plain stem, containment asserted on the resolved path — because it is the
  same shape of bug and this project has already had it once. No write endpoint;
  the view is not editable.
- Markdown rendering. See the bundle constraint above: either a lazy chunk in
  the view, or rendered server-side. Sanitise the output either way. The content
  is authored and trusted today, but a renderer that emits raw HTML is an XSS
  sink the moment that stops being true, and "it is our own file" is exactly the
  assumption that ages badly.
- The embedded reference, with the `frame-src` addition above.
- A Carbon-ish palette for `mkdocs-material`, so the framed site does not look
  like a different product.
- Tier: `public`. Documentation is readable by anyone who can reach the
  dashboard, on any deployment mode. Both endpoints are `GET`, so
  `capabilities.py` already treats them as `PUBLIC`; the routes still need adding
  to the route-table snapshot.

**Done when:** the docs view is in the nav, `/docs/<name>` opens that document
directly, the published reference renders inside the dashboard, a new `.md` file
appears without a code change, a pip install shows a sensible empty state rather
than an error, and the entry bundle is still under budget.

## 4. A judge-config editor that is not painful

**Where it stands.** `LLMJudgeConfigView` is a Carbon `TextArea` holding
`JSON.stringify(config, null, 2)`. No highlighting, no formatting, no structure.
A judge config is a model id, a few generation parameters, and a prompt template
that is a long multi-line string — which is the worst case for a plain textarea:
the prompt dominates the box, the braces that matter scroll off, and a single
missing comma is found by reading rather than by being shown.

The editor also presents JSON for a file that is YAML on disk. That conversion
is lossless in both directions and the round trip works, but it means the thing
being edited does not look like the thing being stored.

**What to build.**

- Syntax highlighting and bracket matching for the JSON. CodeMirror 6 with only
  the JSON language and a minimal extension set is the usual answer; it is
  perhaps 100–150 KB, which does not fit the 42 KB of entry-bundle headroom, so
  it must land in the view's own lazy chunk. The view is already lazy-loaded, so
  this is a matter of importing it in the right place rather than new machinery.
- A **Format** action that reformats the document, and inline error reporting
  that points at the line and column rather than saying "invalid JSON". The
  parse already happens on save; it should happen as you type and show where.
- Keep the existing behaviour that a save is refused when `model.id` or
  `prompt_template` is missing. Highlighting makes malformed JSON visible;
  it does nothing about a config that is valid JSON and a useless judge.

**Consider, do not assume:** editing YAML directly instead of JSON. It matches
the file on disk, handles the multi-line prompt far more gracefully than a JSON
string full of `\n`, and CodeMirror has a YAML mode. It is a bigger change than
highlighting, and it changes what the endpoint receives, so it belongs in this
item only if it is decided deliberately rather than drifted into.

**Done when:** the config is highlighted, a Format action reflows it, an invalid
document says where it is wrong, and the entry bundle is still under budget.
