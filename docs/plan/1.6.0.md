# 1.6.0 — plan

Status: opened 2026-09-01 against `main` at 1.5.0. Five items written up; the
rest of the release is not yet decided. This document is deleted once the release
ships, as [the attic's rule](../attic/README.md) says.

Seeded from what 1.5.0's own release turned up. The background is in
[`../attic/project-log.md`](../attic/project-log.md) — the entry titled *the
release automation failed on the release it was written for*.

## 1. The release workflow needs a rehearsal that reaches every job

**Where it stands.** Pushing `v1.5.0` built the artifacts, verified the tag
against the packaged version, waited on the `pypi` environment gate, published
to PyPI — and then failed on the last job:

```
gh: failed to run git: fatal: not a git repository
```

`github-release` downloads two artifacts and runs `gh release create`. It never
checks the repository out, because it has no need of the source, so `gh` had no
git remote to infer the repository from. Fixed in `531e9d5` by naming the
repository through `GH_REPO`, which is cheaper than cloning to give `gh` its
bearings.

**Why the fix is not the interesting part.** That job was added in 1.5.0
*specifically* because the Release page had been written by hand and forgotten on
1.3.0 and 1.4.0. It failed the first time it was asked to do the job it existed
for. The question worth answering is why nothing caught it.

`release.yml` already has a `workflow_dispatch` trigger, defaulting to TestPyPI,
and it looks like the rehearsal path. It is not, for this job:

```yaml
github-release:
  needs: publish
  if: startsWith(github.ref, 'refs/tags/v')
```

A `workflow_dispatch` from a branch has `github.ref` of `refs/heads/<branch>`, so
the condition is false and the job is skipped. **The rehearsal path structurally
excludes the only job that had never run.** Dispatching from a tag ref would
reach it, but nothing says so and it is not what anyone would try first.

So the gap is not "we forgot to rehearse". It is that the workflow's own dry-run
mode cannot exercise the step most likely to be wrong — a step that talks to a
different API, with different credentials, than everything before it.

**Options, roughly in increasing order of change.**

1. **Document the tag-ref dispatch.** A line in `CONTRIBUTING.md`: rehearse by
   dispatching from a throwaway tag, not from a branch. Cheapest, and relies on
   somebody reading it — which is the same failure mode as the hand-written
   Release page this job replaced.
2. **Let a dispatch reach the job in draft.** Widen the condition to also run on
   `workflow_dispatch`, and pass `--draft` when there is no real tag, so the
   rehearsal produces a page nobody sees and the run can delete it again.
   Exercises the real `gh` call, the real token, the real artifacts.
3. **Make the ordering survive a failure.** `publish` runs before
   `github-release`, which is why 1.5.0's blast radius was one missing page
   rather than a burned version number. That ordering was deliberate and should
   stay — but it means every future failure in the last job lands *after* the
   irreversible step. Worth considering whether the page should be created as a
   draft before publishing and published after, so a failure in either direction
   leaves something recoverable.

(2) is the smallest change that would actually have caught this. (3) is a
question, not a decision.

**Done when.**

- A `workflow_dispatch` run exercises `gh release create` end to end, against
  real artifacts and the real token, without a tag and without leaving a Release
  behind.
- A deliberately broken `github-release` step fails that dispatch, not the next
  real tag. Check this by breaking it on purpose once.
- `CONTRIBUTING.md`'s release section says how to rehearse, and what the
  rehearsal does and does not cover.

**What is already true and should not be re-litigated.** The `pypi` environment
gate works: it is armed with a required reviewer, and 1.5.0's publish waited for
that approval before uploading. The changelog extraction is unit-tested and
fails a tag whose version has no section. Neither needs work.

## 2. The deployed dashboard ran out of file descriptors

**What happened.** On 2026-09-11 the public dashboard listed every benchmark with
no pipelines and could not load any of them. `/api/benchmarks` alternated between
200 and 500, some requests got 502 and a static asset was cut off mid-stream —
while `/api/me`, the healthcheck, answered 200 on every probe.
`docker compose up -d --force-recreate app` brought it back. The account is in
[`../attic/project-log.md`](../attic/project-log.md), under *the dashboard ran
out of files, and its healthcheck said it was fine*.

**Cause.**

- Not memory: nothing in the kernel log, and `OOMKilled=false`.
- The app container's soft `nofile` limit was 1024 (hard 524288) — Docker's
  default. Python, unlike caddy's Go runtime, does not raise it.
- `indexing/builder.py:is_stale` read the index's fingerprint inside
  `with sqlite3.connect(...) as conn:`. A connection's context manager commits or
  rolls back and leaves the connection open, and a connection refers to itself
  through its statement cache, so dropping it does not close it either — only the
  cyclic collector does. `get_index()` calls `is_stale` on every cached lookup,
  so each `/api/benchmarks` left six descriptors, one per index. Measured on the
  live app after the restart: 49 → 55 → 61 → 67 → 73, then 29 when a collection
  ran.
- `JudgeStore` used the same idiom in every method, so each `/api/me` from a
  caller at judge tier left one on `judge/usage.sqlite`. Measured locally: ten
  calls, ten descriptors.

A first diagnosis blamed `EvalIndex._open_connections` for keeping the
connections of retired worker threads. A fix for that was written and
unit-tested before a local server on it showed the count still climbing, with
back-to-back requests and no new threads at all. That leak is real but small —
see *What changed* — and was not the cause.

Not established: the old process's own error, whose logs went with the
container, and how long it took to reach 1024.

**What changed.**

1. `is_stale` closes its connection, and `JudgeStore._connect` is a context
   manager that commits or rolls back and then closes.
   `tests/test_connection_leaks.py` records every connection opened and requires
   each to be closed on return; three of its four tests fail against 1.5.0's
   code. The fourth checks the ledger still commits, since `set_user_cap` relied
   on the old context manager for that.
2. `EvalIndex` records the thread that owns each connection and, when opening a
   new one, closes those whose thread has exited: anyio retires idle workers
   after a burst of requests, and the list kept their connections until the
   index was dropped. Covered in `tests/test_index_concurrency.py`.
3. `deploy/docker-compose.yml` raises the app's `nofile` limit to 65536, and the
   CI compose check fails a file that drops it.
4. `docs/dashboard/deployment.md` has a troubleshooting row for the symptom.

Checked against a local server on the fixed code: index descriptors stayed at six
across eight back-to-back `/api/benchmarks` calls and three more after idle gaps,
and twenty calls to `/api/me` and `/api/deployment` left none on the ledger.

**A stopgap on the host, to be removed.** Root's crontab on the deployment runs
`/usr/local/bin/text2sql-dashboard-restart` at 03:17 and 15:17 UTC. It appends
the app's open-descriptor count to `/var/log/text2sql-dashboard-restart.log`,
then runs `docker compose restart app`. It is there until the fix is deployed.

**Done when.**

- The fix is deployed with `up -d` rather than `restart` — `ulimits` applies
  when a container is created — and `docker compose exec app sh -c 'ulimit -n'`
  prints 65536.
- The restart log shows the descriptor count flat across several twelve-hour
  periods. It records the count *before* each restart for exactly this.
- The cron entry and the script are removed from the host.

**Noticed, not done.**

- **The healthcheck could not see it.** For an anonymous caller `/api/me` opens
  nothing new per request — its roles connection is per thread and already
  open — so it passed while the page it stands for was broken, and
  `restart: unless-stopped` does not act on an unhealthy container in any case. A
  check that reads something from the data root would at least have marked it
  unhealthy.
- **The landing page reported the failure as data.** `list_benchmarks` catches
  every error from counting records and pipelines and falls back to zero, so a
  process that could not open a file showed "0 pipelines" rather than an error —
  the wrong-answer-rather-than-error shape `test_index_concurrency.py` exists to
  prevent.
- **The host's disk is 83% full**, 30 of 38 GB, against 8.3 GB measured after the
  first provisioning.
- **`is_stale` still opens the index on every lookup.** It closes it now, but it
  is still a file open and a query per cached hit; comparing against the
  fingerprint the cached handle was opened with would avoid both.
- `ui/roles.py` and `ui/user_keys.py` hold a connection per thread and keep no
  list. A retired thread's connection there waits for the cyclic collector like
  any other unclosed one — bounded by thread turnover; not measured.
- `execute_query` over an in-memory database in `metrics/text2sql_utils.py` never
  closes its connection. No descriptor, only memory until a collection.

## 3. Archer's LLM-judge results: commit, publish, redeploy

**Where it stands.** `archer_en_dev` was the only benchmark with no LLM-judge
scores at all — for all 11 pipelines, not only the Gemini one — which is why
`/insights?benchmark=archer_en_dev` shows *No evidence available* under *LLM judge
comparison*. On 2026-09-01 the judge was run with `rerun_metrics.py
--use-llm-judge` and `llm_judge_default_config`
(`wxai:meta-llama/llama-3-3-70b-instruct`), verified identical, model and prompt,
to the judge config recorded in the existing summary.

- 1,093 of 1,144 predictions scored: 543 Yes, 550 No. The other 51 are agentic
  predictions with no SQL at all — 20 in `baseline4`, 31 in `baseline5` — and
  those two pipelines have unscored predictions on other benchmarks too.
- Regenerated from that data on 2026-09-11: the eval JSON, the summary
  `.json`/`.csv`/`.md`, the errors report and the seven charts. `num_correct_llm`
  in the summary JSON and CSV matches the raw scores for every pipeline.
- `archer_en_dev-predictions.json` is byte-identical to HEAD, and the eval file
  keeps HEAD's formatting and key order, so its diff is only the 1,093
  `llm_score` and `llm_explanation` lines and the trailing commas they need.
- The judge-comparison endpoint, queried in-process at the public tier, returns
  evidence for all 11 pipelines.

**None of it is committed.** The 12 archer files are modified in the `1.6.0`
working tree only.

**Remaining.**

1. **Commit** the 12 archer files, leaving `data/judge/usage.sqlite` out (see
   *Carried over*).
2. **Decide the Hub revision.** `results fetch` defaults to the tag matching the
   installed toolkit version, and `v1.5.0` points at dataset commit `3a59f43`. An
   upload to `main` alone reaches no 1.5.0 install, and the deployment fetches a
   pinned snapshot (`REVISION` in `deploy/provision.sh`). Either move `v1.5.0` —
   changing a snapshot 1.5.0 users were given as reproducible — or publish under a
   new tag and point the deployment at it.
3. **Before uploading, decide about the stale Gemini rows.** The summaries for
   `bird_mini_dev_postgres`, `bird_mini_dev_sqlite`, `spider_dev` and
   `spider_realistic` list `gemini:gemini-3-flash-preview-greedy-zero-shot-chatapi`,
   but none of those benchmarks' predictions or eval files contain it.
   Regenerating their summaries would drop the rows. Gemini results for those four
   would be a new inference run, not a judge run.
4. **Upload** to `text2sql-eval-toolkit/text2sql-eval-results`.
5. **Redeploy through provisioning, not by copying files.** Index staleness is
   decided by the eval file's content fingerprint, and on a shared deployment a
   stale index is never rebuilt on request: every archer view — not just the judge
   panel — answers 503 *This benchmark is not ready to serve yet* until
   `text2sql-eval-toolkit index build` has run. `deploy/provision.sh` fetches,
   builds and checks `index status`; a manual file swap does none of that.
   Checked locally: stale index, 503 at the public tier; rebuilt, 200.

**Done when.**

- The archer changes are committed, and on the Hub under a revision the
  deployment fetches.
- On the deployment, `/insights?benchmark=archer_en_dev` shows the LLM judge
  comparison for all 11 pipelines, and no archer view answers 503.
- No published summary lists a pipeline its own eval file does not contain.

**Noticed, not done.**

- **`rerun_metrics.py <benchmark_id> --in-place` writes over the predictions
  file**, not the eval file (`scripts/evaluation/rerun_metrics.py:208-209`). That
  is how the first archer run landed in `archer_en_dev-predictions.json`. With
  `--input-file …_eval.json` the flag does what its name says; with a benchmark id
  it does the opposite. It should target the eval file, or refuse.
- **`make_summary_report.py` is the documented command and was the wrong one
  here.** It rewrites `data/results/README.md` — the hand-written Hub download
  guide, the known trap recorded in the project log on 2026-08-25 and still unfixed
  — and regenerates every benchmark's summary and errors report on the way. One
  benchmark's report needed `export_summary_results_by_category_to_markdown` called
  directly; there is no command for that.
- **The summary report's "Predictions #" column is always 0.** It reads
  `num_predictions`, which nothing computes.
- **The chart legend covers the first LLM Score bars**, now that those bars are no
  longer zero.

## 4. gpt-oss-120b: new baselines and new judge configs

**Asked for.** New baselines, and new LLM-judge configs, using gpt-oss-120b.
Which baselines count as new is not yet written down; that is the first thing to
settle.

**Where it stands.**

- **Baselines.** Every benchmark already has gpt-oss-120b predictions:
  `wxai:openai/gpt-oss-120b-greedy-zero-shot-chatapi` and
  `…-agentic-baseline0-3attempts` through `baseline5`. A pipeline id is derived,
  not configured (see `CLAUDE.md`), so a new baseline means a new model string,
  pipeline version or attempt count — not a new name.
- **Judge configs.** None of the four packaged configs uses gpt-oss-120b:
  `llm_judge_default_config` and `llm_judge_no_gt_v1` use
  `llama-3-3-70b-instruct`; `llm_judge_alt_config` and `llm_judge_no_gt_v2` use
  `llama-4-maverick-17b-128e-instruct-fp8`. Adding one is a YAML file, or Duplicate
  in the dashboard's config editor.

**The constraint that makes this more than a config file.** Each prediction has
one judge slot — a single `llm_score` and `llm_explanation` — and a summary
records one `llm_judge_config`. The batch judge reuses any existing score without
checking which config produced it
(`src/text2sql_eval_toolkit/evaluation/evaluation_tools.py:295-300`). So running a
gpt-oss-120b config over results that already have llama scores does one of two
wrong things:

- without `--force-rerun-llm-judge`, it keeps every llama score and records the
  gpt-oss-120b config in the summary — results labelled with a judge that did not
  produce them;
- with it, it replaces the llama scores, and the cross-benchmark comparison
  changes judge without saying so.

The dashboard's on-demand verdict cache does not have this problem: it is keyed on
the config's contents.

**Open questions.**

- **Replace or add?** If gpt-oss-120b *replaces* llama-3-3-70b as the published
  judge, that is a full re-judge and a changelog entry. If it sits *alongside*,
  scores need per-config storage — keyed in the evaluation block, or a file per
  judge — and the dashboard needs a way to choose between them.
- **Should the batch cache be keyed on the config**, as the dashboard's already
  is? Either way, reuse across configs should stop being silent.
- **Cost.** Archer's 1,144 judge calls took 17.6 minutes at concurrency 16. The
  whole corpus is roughly 28,700 predictions, about 25 times that, and Beaver's may
  cost far more per call: the prompt template includes both result dataframes, and
  some Beaver results run to tens of thousands of rows.

**Done when.**

- The new baselines are named in this item, then run, evaluated and published
  like the existing ones.
- A gpt-oss-120b judge config exists, and its scores are stored so that no result
  is labelled with a judge that did not produce it.
- If both judges are kept, the dashboard shows which one a score came from.

## 5. Beaver: visible only when signed in, and not indexed

**Asked for.** The Beaver benchmark should not be visible without logging in, and
should not be indexed by search engines.

**Where it stands.**

- **Nothing in the dashboard is per-benchmark.** Every read route is public tier
  (`ui/capabilities.py`: "Read routes need no entry: they are PUBLIC"), so Beaver's
  summary, error analysis, record detail, playground, insights and exports answer
  anyone, as does its logo at `/api/static/benchmarks/logos/beaver.png`.
- **The tiers cannot express "signed in".** An anonymous visitor and a signed-in
  user with the default `read_only` role are the same `public` tier
  (`docs/dashboard/capability-tiers.md`). Gating on login is a check on identity,
  not a tier setting.
- **Nothing addresses crawlers.** There is no `robots.txt`, no `noindex` meta tag
  and no `X-Robots-Tag` header — not in the app, the SPA shell or the Caddyfile.
  The SPA shell answers 200 at every client path, `/benchmark/beaver` included.

**Beaver is public in more places than the dashboard.** Gating the dashboard hides
the page, not the data:

- **GitHub.** The repository tracks `data/benchmarks/beaver.json`,
  `beaver-schema.json` and `beaver-original.json`, the 10-question test subset with
  its results, and `data/results/beaver-predictions_eval_summary.md`, the errors
  report — which quotes questions and SQL — and the charts.
- **Hugging Face.** `text2sql-eval-toolkit/text2sql-eval-results` is public and
  ungated, with 14 Beaver files, and `results fetch --benchmarks beaver` downloads
  them without an account. Hub gating applies to a whole repository, so Beaver
  would need one of its own.
- **The deployment image** copies `data/benchmarks/*.json`.
- **Docs.** The dashboard tour's home-page screenshot and its description name
  Beaver, as does `README.md`. The survey mentions it four times as part of the
  literature it reviews.

**Open questions.**

- **Dashboard only, or everywhere?** This sets the size of the item more than
  anything else. If the concern is who may see the data, the GitHub and Hub copies
  matter as much as the page.
- **Signed in, or a role?** A user who signs in gets `read_only` by default. If
  Beaver should be limited to specific people, gate it on a granted role rather
  than on sign-in.
- **Crawlers.** A login wall keeps the data out of search results by itself;
  `X-Robots-Tag: noindex` on Beaver's routes keeps the addresses and titles out
  too. A `robots.txt` entry is only advisory, and publishes the very paths it asks
  crawlers to skip.

**Done when.**

- An anonymous request to every Beaver-scoped route is refused, enforced by a
  test that enumerates the routes — the way `tests/test_route_table.py` does for
  tiers — so a new route cannot quietly expose it.
- Beaver is absent from the anonymous `/api/benchmarks` and home page, and present
  for a signed-in user (or the chosen role).
- A shared Beaver link opened anonymously asks the reader to sign in, rather than
  showing a not-found or an empty page.
- Beaver's responses carry `noindex`.
- The GitHub and Hub copies are handled however the first open question is
  answered.

## Carried over from 1.5.0

Small things noticed while working on 1.5.0 and deliberately left alone, recorded
here so they are not lost. None is urgent; none has been investigated beyond the
observation.

- **`data/judge/usage.sqlite` is tracked in git.** The running dashboard writes
  to it, so it shows as modified after any local run and had to be reverted out
  of several commits this cycle. It was committed once, in `716d1be`, and looks
  accidental — it is runtime state, not fixture data. Probably belongs in
  `.gitignore` with the tracked copy removed, but check first whether anything
  reads it as a seed.

- **Playwright silently adopts a stray local server.** `playwright.config.ts`
  sets `reuseExistingServer: !process.env.CI`, so any dashboard already
  listening on 8123 becomes the system under test. During 1.5.0 a forgotten
  server served a stale build and five tests failed with a different five on each
  run, which is the only reason it was noticed rather than believed. Correct in
  CI, where the flag is false. Options: check the served build's identity before
  trusting it, or stop reusing and take the startup cost.

- **Carbon keeps the "Add New Benchmark" modal mounted with
  `aria-modal="true"` on every page**, including `/docs`, where there is no such
  control. Pre-existing and Carbon's own pattern — the visibility state lives on
  a wrapper — so it may well be fine. Worth a look if there is ever an
  accessibility pass; not worth a change on suspicion.

- **The docs directory is discovered, never configured.** 1.5.0 restricted the
  walk to an ancestor whose `pyproject.toml` declares this project, which closed
  a public-tier disclosure path. The consequence is that a `pip install` serving
  notes from an arbitrary directory is no longer possible at all. If that is
  ever wanted, it should be an explicit setting rather than a side effect of
  where the process was started.
